# Performance smoke harness — dataset and command

The harness is `tests/performance/run-smoke.ps1`. This file is the part
that makes its numbers mean something: **a performance claim without a
dataset and a command is not evidence** (plan.md §7.3).

## Synthetic dataset

Every measurement below is against a **disposable** database that the
harness itself creates and drops. No customer data, no production row
counts, no `.env`. The seed is `tests/performance/dataset.sql`.

The volumes are chosen to sit at and just above the point where the
`PROJECT_REQUIREMENTS §7` targets start to mean something, while staying
small enough that a developer laptop can run the smoke in under a minute.

Measured on a throwaway carrying the whole Flyway chain, 2026-10-04. The
row counts below are what `dataset.sql` actually wrote, not what it intended
to write; it prints them at the end, because a seed that silently seeds
nothing is worse than a seed that fails.

## What is measured, and against which target

`PROJECT_REQUIREMENTS §7` states the targets; `tests/performance/thresholds.json`
carries the same numbers as machine-readable assertions.

| Scenario | Request | Target (p95) |
| --- | --- | --- |
| customer list, first page | `GET /api/v1/customers` | 500 ms |
| customer 360 | `GET /api/v1/customers/{id}` | 500 ms |
| conversation detail + transcript | `GET /api/v1/conversations/{id}/transcript` | 500 ms |
| inbox page | `GET /api/v1/conversations` | 500 ms, and **first inbox page within 1.5 s** end to end |
| unassigned queue page | `GET /api/v1/inbox/unassigned` | 500 ms |
| note list | `GET /api/v1/notes` | 500 ms |
| mutation, no provider call | `PATCH /api/v1/customers/{id}` | 800 ms |

Per run the harness records, for every scenario and overall:

- `p50`, `p95`, `p99` latency in milliseconds (nearest-rank, so each
  percentile is a number a request actually took);
- error rate as failed requests / total;
- heap and RSS of the API process, sampled before and after;
- PostgreSQL connections in use and `max_connections`;
- queue lag: oldest pending `outbox_events` age and pending count, and the
  worker's reported lag if the management port exposes it;
- the exact command, the dataset row counts and the target base URL, so
  the numbers can be reproduced.

## Command

```powershell
# one-off: start the API against a disposable, seeded database
.\tests\performance\run-smoke.ps1 -TargetBaseUrl http://localhost:8080 `
    -Container firstelement-postgres -Iterations 200 -Warmup 20 `
    -Report build\quality-evidence\performance.json
```

Through the gate runner (what CI does):

```powershell
.\ops\quality\run-gates.ps1 -Stages performance-smoke
```

## Why it fails instead of skipping

If the target service is unreachable, the harness **fails** and prints the
exact command to start it. It never reports a pass it did not measure. A
performance gate that reports "skipped" is worse than no gate, because it
turns "we do not know" into "it is fine" in a dashboard.

Telemetry (memory, connections, queue lag) is also mandatory. If a source
is unavailable the harness records `null` **and** fails, naming which source
and why. The only way through is an entry in
`ops/quality/waivers/pending-stages.allow.json` naming the stage.

## Known limitation

Queue-lag and connection telemetry read the database and the management
port directly. They are *observations*, not an assertion about the
dispatcher: `outbox_events` pending count and oldest-pending age are what
an operator sees, and the worker's own lag metric is compared against them
when the management port exposes it. The full capacity test (sustained load,
export throughput, database failover simulation) belongs to the phase that
owns the corresponding module and is out of scope for a smoke.
