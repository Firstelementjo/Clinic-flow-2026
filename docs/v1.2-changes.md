# V1.2 — agent workspace, case handling, metrics

What `FE-CRM-V1.2.md` asked for, what was built, and the decisions that
were not spelled out in the spec.

## About the spec document

Three problems in the file worth recording, because they shaped the work:

- It opens with `Analysis errored` and ends with stray Python that wrote
  it. **Sections 2 and 3 are missing** — it jumps from `#1` to `#4`.
- `#1` is titled "Logout / Sign Out" but its body describes employee
  creation. The `§22` summary is internally consistent, so that was
  treated as the authoritative list.
- `§23` explicitly defers the four classification questions, their answer
  options, and the classification-to-solution mapping. All three are
  therefore **data, not code**.

If §2–§3 held real requirements, they are not recoverable from this file.

## Authentication

Sign-out was broken in a way the server logs did not show. The API
returned `204` and revoked the session correctly, but the browser reported
the request as `net::ERR_ABORTED`, so the client's `onSuccess` never ran:
the cache kept its data and the UI kept rendering the app shell over a
dead session, with every later request 401ing.

Teardown now runs on settle rather than success. Logging out locally
without server confirmation is the safe direction — a stale server session
expires on its own, while a UI that believes you are still signed in does
not.

## Agent status and time (§8, §9)

Seven statuses: Online, Offline, Busy, Break, Meal, Training, Meeting.
Only **Online and Busy are routable**; the rest are stated reasons for
being away, which is what makes the time report worth reading.

Each change closes the open `AgentStatusSession` and opens a new one **in
one transaction** — a crash between the two writes would otherwise leave
either a double-counted overlap or a gap in the day.

The timer counts from a server-issued `since`, never from a local start.
A refresh, a second tab, or a laptop asleep for an hour all show the same
elapsed time, and it is the same number the totals report on.

## Employee administration (§1, §4, §5)

Create accounts with credentials, activate and deactivate, assign and
reassign projects, and set each agent's conversation limit — all from the
Team screen, no database access required.

The limit is enforced where it matters: `selectAssignee` filters on
`activeConversationCount < maxConcurrentConversations`, so an agent at
capacity receives nothing until their load drops. Nothing is hard-coded to
five; five is only the column default.

## Case classification (§12, §13, §23)

Questions and their options are configured per project and stored as data.
Four is the expected count, not a schema limit, and the wording arrives
later without a deploy.

Answering resolves a solution in two steps:

1. An admin-configured **mapping** from answers to a specific document —
   the deterministic path §23 anticipates.
2. Otherwise a **knowledge search** using the chosen answers' readable
   labels as the query.

Both are scoped to the conversation's own project, so a case in project A
can never surface project B's solution. The stored answers are kept
verbatim, so editing a question later does not silently rewrite what an
agent actually answered.

## Solution record and case state (§14, §15)

The resolution captures the issue, the action, whether the knowledge base
answer was used, whether the customer accepted it, satisfaction,
escalation requested and performed, outcome, and notes.

Satisfaction is deliberately three-state — yes, no, **not recorded**. An
unanswered question must not count as a dissatisfied customer.

Closing a case requires a resolution record. A case closed with no account
of how it ended is the exact gap §14 exists to prevent. Reopening clears
the closed state but keeps the resolution: it is history, not current
state.

## Metrics (§22)

CSAT, DSAT, resolve rate, first response time, average handling time and
cases resolved, alongside the existing AI and escalation figures.

Two definitions worth stating:

- **Average handling time is first response → resolution**, not
  creation → resolution. The latter would bill a conversation that waited
  overnight in the queue as handling time.
- **CSAT and DSAT are agent-reported.** Nothing in this build asks the
  customer directly; the agent records whether the customer seemed
  satisfied, per §14. They are an internal quality signal, not survey
  results, and should not be presented as the latter. A real customer
  survey is a separate feature.

Both render `—` rather than `0%` when nothing has been rated, because "no
data" and "everyone was unhappy" must not look identical.

## Floating inbox (§16–§19)

The complete workspace — conversation list, active conversation, customer
details, classification, solution, resolution, case actions — in a
draggable, resizable, minimizable window **inside the app**, explicitly not
a browser popup or a second tab.

It is hosted in the shell rather than the inbox route, which is the whole
point: the agent pops it out, navigates to knowledge or analytics, and the
conversation stays visible and live because that subtree never unmounts.
Minimizing hides the body with CSS instead of unmounting it, so an
in-flight reply and the scroll position survive. Geometry persists to
`localStorage`.

Its selection is its own, independent of the page behind it. A floating
window showing one conversation while the page shows another is what
"keep the chat visible while I look something up" means in practice.

## Bugs found along the way

Three were pre-existing and unrelated to the V1.2 requests:

- **`yarn dev:api` could never start.** `deleteOutDir: true` in
  `nest-cli.json` wiped `dist/` while TypeScript's incremental build info
  said "already built", so the API compiled cleanly and then had no
  `dist/main` to run.
- **Config only looked for `.env` in the working directory.** Nest runs
  from `apps/api`, so it never found the repository root's file.
- **Every timestamp defaulted by the database was wrong.** See
  docs/deployment.md — Prisma reads `timestamp without time zone` as UTC
  while PostgreSQL fills defaults with server-local time. On a database in
  `Asia/Amman` every such row landed three hours in the future, quietly
  skewing analytics windows, response times and inbox ordering.

And one that had been hiding the rest:

- **Vitest never loaded `.env`**, so `DATABASE_URL` was absent from the
  test process and *every* integration suite skipped itself — silently,
  because a skip is not a failure. The suites proving tenant isolation and
  RAG isolation had never run. They run now, and pass.

Fixing that immediately surfaced two genuine defects the skipped tests
would have caught much earlier:

- The mock provider treated a **failed** tool result as knowledge and
  answered a customer with `{"results":[],"found":false}`.
- The system prompt's security policy contained the literal string
  `<knowledge>` while explaining that knowledge blocks are data — giving
  anything parsing the prompt a decoy delimiter that paired with the real
  closing tag. The policy now names the block without quoting its tag,
  and there is a regression test.
